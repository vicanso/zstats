# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

zstats is a system performance metrics collection library + CLI tool (Rust, edition 2024). The design spec lives in `collector-core-design.md` — note the crate is named `collector-core` there, but the code was merged into the single `zstats` crate (lib + bin). The API follows the spec with one deviation: disk, network, and process collection are each toggleable in `CollectorConfig`, so their snapshot fields are all `Option<...>` (`None` means "not collected", not "none found"; processes are `Option<Arc<Vec<_>>>` so snapshot clones share the process table). CPU, memory, and load are always collected — they cost only microseconds. The lib is `#![forbid(unsafe_code)]` — platform FFI must go through a safe-wrapper dependency (user decision; the `sysctl` crate is the current one, macOS-target-scoped), never a hand-written `unsafe extern` in lib code. On heterogeneous CPUs (Apple Silicon), `CpuSnapshot::perf_levels` reports per-cluster (P/E) average usage: topology is read once at startup via public sysctls (`hw.nperflevels` / `hw.perflevelN.*`), and usage is a pure partition of the per-core sample. `MemorySnapshot::{compressed_bytes, pressure_level}` (macOS) read `vm.compressor_bytes_used` and `kern.memorystatus_vm_pressure_level` (1/2/4 = normal/warning/critical) each collect — compressor growth, not used%, is the real pressure signal; pagein/pageout RATES were deliberately skipped because they exist only via Mach `host_statistics64`, which would require unsafe FFI in zstats. Core numbering starts with the LOWEST level (E-cores first — verified empirically with a background-QoS load) while `perflevel0` is the highest, so `split_perf_levels` reads from the tail backwards; any topology/core-count mismatch yields `None` rather than wrong numbers. Dynamic per-cluster frequency/power are deliberately out of scope (root-only powermetrics / private IOReport). The expensive parts are throttled: disk capacity (statfs, ~18ms on macOS) refreshes on its own slow cadence (`disk_storage_refresh_interval`, default 60s) while disk IO counters (~0.7ms) refresh every collect by default — with one exception: sysinfo's enumeration picks a volume up the moment it is mounted but fills a brand-new entry's capacity with 0 unless storage was requested, so a fresh mount would read 0/0 for up to a full storage interval (and `dedupe_disks`, which prefers the shortest mount point, could let that zero entry win over a healthy mount of the same device); `collect_disks` therefore calls the per-disk `refresh_specifics(with_storage())` on exactly the mounts that were absent from the previous refresh (`is_new_mount`, keyed on `disk_key` = `name:mount_point`), which leaves every other volume's cadence and every IO counter untouched — the platform impls all gate `refresh_io` on `io_usage()`. Nothing counts as new before a refresh has recorded a mount set, since the constructor's enumeration already carried capacity; CPU frequency refreshes every `cpu_frequency_refresh_interval` (default 30s); processes (~9ms) are the second-largest cost and can run on their own cadence (`process_refresh_interval`; the `serve` CLI defaults it to 10s). Every subsystem except CPU usage and memory has an independent cadence knob: `disk_io_refresh_interval` and `network_refresh_interval` (both default 0 = every collect, CLI `--disk-interval`/`--network-interval`) reuse the cached snapshot lists between refreshes, with rate diffs spanning the time since that subsystem's own previous refresh — there is no global `last_collect_time` anymore. Process selection ranks by CPU/memory first and only then materializes name/cmd strings for the top-N. `collect_process_groups` (default true, requires `collect_processes`; `-add process-groups`) additionally aggregates whole process trees into per-application groups (`SystemSnapshot::process_groups`, `Option<Arc<Vec<_>>>` like processes): root = ancestor whose parent is init/launchd (pid 1), summed over every descendant — this is computed over the FULL table before top-N truncation (deliberately: summing after truncation would systematically undercount many-small-helper apps like Chrome), costs one in-memory pass on the process cadence with no extra syscalls, and is capped at `max_processes` groups ranked by CPU. Known semantics on macOS: each terminal shell session groups under its `login` root (launchd child), not under the terminal app's own group. Groups also carry summed disk IO rates when `collect_process_disk_io` is on (summed over the FULL table, so a group total covers members that never ranked into the top-N), and `ProcessSnapshot::user_id` rides along free via `with_user(OnlyIfNotSet)`. Thread counts were evaluated and skipped: sysinfo's `tasks()` is documented Linux-only and returns nothing on macOS. Disk IOPS/latency/util and swap in/out RATES were also evaluated and rejected for now — sysinfo exposes only byte counters, macOS needs IOKit (IOBlockStorageDriver) or Mach `host_statistics64` for those, both unsafe FFI; the `vm.compressor.segment.*` sysctls look like counters but are state gauges (observed decreasing), so deriving rates from them would print wrong numbers. While overall load is at or above `process_boost_cpu_cores` logical cores of work (default 2.0 — a modern desktop's ambient load is already ~1 core, so 1.0 kept the boost pinned on all day at ~1.4% daemon CPU vs ~0.6% unboosted, measured A/B; the boost only refines attribution granularity, alert correctness never depends on it), the process list refreshes every collect regardless — CPU/memory are refreshed first inside `collect()` precisely so this decision can use the fresh value. `collect_process_disk_io` (default false) optionally adds per-process disk rates; `dedupe_disks` (default true) collapses APFS multi-mount volumes by device name. `collect_battery` (default true, `battery_refresh_interval` 30s) reads the main battery — charge, health/wear, cycles, temperature, present watts — via the `starship-battery` crate (a safe wrapper, so the `forbid(unsafe_code)` rule holds); machines without one report `None`, and only the first battery is reported since a merged total across several would be meaningless. Measured cost: 0.63ms per read, i.e. 0.002% CPU at the default cadence. Scope decision (user, after challenging whether battery is worth collecting at all): keep it as a METRIC but never add a battery alert rule — low-battery warnings are the OS's job and a second one is pure noise; charge% duplicates the menu bar and health/cycles move over months, so `power_watts` (dynamic, and surfaced nowhere in the macOS UI) is the field that actually justifies the subsystem.

The module's scope is **collecting local machine data only**: the "remote Collector (pulling snapshots from other machines via gRPC/HTTP)" extension mentioned in section 12 of the design doc has been explicitly rejected — do not design abstractions or features for it.

## Architecture

The data flow is a one-way pipeline. `SystemSnapshot` (`src/snapshot.rs`) is the single data contract inside and outside the module:

```
Collector (trait, sync) ──SystemSnapshot──▶ Scheduler ──concurrent dispatch──▶ MetricSink (async trait) × N
```

Key designs that span multiple files:

- **Rate metrics rely on diffing state**: `LocalCollector` (`src/collector/local.rs`) keeps the previous sample's cumulative disk/network counters and an `Instant`, computing per-second values via `rate_per_sec` in `utils/rate.rs` (counter wraparound yields 0). Therefore **the first collect returns None/0 for rates** — both the tests and the CLI one-shot mode deliberately sample twice because of this. `Collector` is a stateful `&mut self` object; do not casually rebuild it.
- **The sync-collection / async-scheduling boundary**: `Collector::collect` is synchronous (sysinfo is a sync API). `Scheduler` (`src/scheduler.rs`) wraps it in `spawn_blocking`; the collector is shared between the scheduling loop and `collect_once` via `Arc<Mutex<Box<dyn Collector>>>`. `collect_timeout` bounds how long the loop WAITS, not how long a collect runs — a blocking task cannot be cancelled, so a stuck collect (statfs on a vanished network mount is the realistic one) runs to completion regardless. Two consequences are designed for: the timeout is read ONCE at `start()` rather than through the collector's lock each round (reaching through the lock blocked a runtime worker — there are only 2 — for as long as the stall lasted), and an `in_flight` AtomicBool makes the loop skip ticks while a collect is still running (`a_stalled_collect_is_not_queued_up_by_every_missed_tick`). Without the skip, every missed tick queued another blocking task behind the same lock and they all fired at once on release.
- **Sink failure isolation**: each sink's `write` runs concurrently in its own task with its own timeout (default 5s); a failing/slow sink only produces a tracing log and never affects other sinks, and a failed collect just skips the round. Adding a backend only requires implementing `MetricSink` (`async_trait` is re-exported from lib.rs). `MetricSink` must stay dyn-compatible (`Arc<dyn MetricSink>`), which is why `async-trait` is used instead of native async fn in traits.
- **Scheduling policy**: `tokio::time::interval` + `MissedTickBehavior::Skip` — when a collect overruns the interval, missed ticks are skipped, never replayed.

The InfluxDB / Prometheus sinks from the design doc (P1/P2) are not implemented yet; the `src/sink/` layout is reserved for them.

## Cargo Features

Local collection is the core capability: sysinfo/`LocalCollector` are always available and never feature-gated. The default feature is `cli` (full functionality; `cargo build/test/install` behave as usual):

- No features: data contract + synchronous collection (`LocalCollector`), no tokio — for embedders that drive their own scheduling;
- `runtime`: adds `Scheduler` and the `sink` module (pulls in tokio/async-trait/tracing);
- `config`: adds `CollectorConfig::load_from_dir` (toml) — reads `<dir>/config.toml`'s `[collector]` section. All config Durations use `config::duration_serde`: they parse from `"500ms"`/`"2s"`/`"5m"`/`"1h"` strings or bare integers meaning milliseconds (`config::parse_duration`, also used by `-add`), and serialize back as the most compact unit string (`config::format_duration`, so 60000ms round-trips as `"1m"`);
- `client` (unix only, `src/client.rs`): typed client for the daemon's Unix-socket protocol — `socket_path`/`is_running`/`attach`/`stop` (+ `_at` variants taking an explicit path, used by tests and custom sockets). `DaemonStream::next()` yields history snapshots then live ones (`history_remaining()` tells which; garbled lines are skipped but still consume their announced history slot) and is cancel-safe for `select!`. Needs no tokio runtime of its own — the caller drives it. This module exists so every frontend (CLI, future GUI) shares one wire-format definition; the server side stays in the bin;
- `frontend` (requires `config`; sync only, no tokio): the building blocks every frontend shares so CLI and GUI agree on numbers and file formats — `alerts` (Thresholds/ActiveThresholds/AlertEngine: the rule engine with injectable clock; delivery is the frontend's job). `AlertEvent` is pure data, no wording stored — `subject` (AlertSubject: Process/App/Volume/System, carrying the pid or mount to link back to) + `detail` (AlertDetail: every number in the rule's own units, incl. the window and the runaway flag) + `repeat_after` for the 30m follow-up; `kind()`/`severity()` are DERIVED so they cannot disagree with the data, and `summary()` (also `Display`) renders the default English line on demand. This keeps the "lib contains no presentation logic" rule honest — baking a formatted `message` into the event violated it and made localisation impossible. Everything serialises, `rolling` (`ProcessWindows` per-process rolling averages, used by both the alert engine and the CLI's PROC table), `records` (`MetricRecord` + append/read_range/cleanup for the daily jsonl history; all functions take the date explicitly — callers pass `jiff::Zoned::now().date()`), `settings` (the full config.toml model + `apply_add`/`apply_remove` key table; functions take the config dir explicitly, `default_dir()` = `~/.zstats`). `~/.zstats` is the shared directory for EVERY frontend, GUI included (user decision): shared config + metrics history between CLI and GUI outweighs platform-native dir conventions (Application Support / XDG / APPDATA), and the sandbox argument doesn't apply — monitoring apps can't be sandboxed anyway. Precedent: Docker Desktop reads `~/.docker`, GUIs read `~/.ssh`/`~/.aws`. If platform-native dirs are ever wanted, the change is confined to `default_dir()` ("existing `~/.zstats` wins, else platform dir") since every lib API takes the dir explicitly. `monitor` (`Monitor::tick()` → `Tick { snapshot, alerts, process_stats, records }`) is the one-call assembly of all of the above — collect, evaluate, smooth, persist — for frontends that would otherwise hand-wire it; sync and callback-free on purpose (a GUI must control which thread touches the UI, and collection blocks), `reload_settings()` rebuilds thresholds only since `[collector]` changes would discard the rate baselines. `examples/embedded.rs` (required-features frontend+client, kept compiling by `make lint`) is the reference skeleton for a single-process GUI frontend that embeds collection instead of using the daemon — such a frontend must be the ONLY collector (never run alongside `zstats serve`: duplicate alerts and duplicate jsonl records);
- `cli`: client + config + frontend + runtime + bin-only tokio features (signal etc.); the bin is bound via `required-features = ["cli"]`.

The CLI resolves a config directory for every mode (default `~/.zstats`, `--config-dir` overrides; the flag is pre-scanned in main before any settings read). `config.toml` sections: `[collector]` (base for CLI flag overrides), `[daemon]` (`interval_ms`/`history_secs`/`detach`; `--foreground` forces foreground, and detached children always get `--foreground` appended to avoid re-detach loops), `[alerts]`. attach/stop skip config loading so a broken file cannot block stopping a daemon.

When adding a dependency, decide which layer it belongs to first. `make check-features` (included in `make check`) verifies each combination compiles independently — always run it after adding `cfg` gates. The integration tests are gated behind `runtime` as a whole.

Platform policy: macOS is the reference platform (the only one actually run and integration-tested); Linux and Windows must at least keep compiling. `make check-targets` (part of `make check`) cross-checks both targets with warnings-as-errors for this crate (one-time setup: `rustup target add x86_64-unknown-linux-gnu x86_64-pc-windows-msvc`). Rules that keep this cheap: platform-specific metrics are `Option` fields that read `None` elsewhere (perf_levels, compressed_bytes/pressure_level are macOS-only today; their Linux analogues — sysfs cpu capacity, PSI — are known future work); the daemon/client/alerting-delivery layer is unix-only via `cfg(unix)`, so the Windows CLI degrades to the foreground view + `--json` with Ctrl+C instead of q/d keys. Known Windows semantic caveats: load average is sysinfo-emulated from CPU samples, and temperatures are usually empty (WMI) — `collect_temperatures` therefore defaults to FALSE on Windows only, because sysinfo reaches them via `MSAcpi_ThermalZoneTemperature`, which calls `CoInitializeEx` on the collector thread and sets a process-global `CoInitializeSecurity` every cadence; that is an integration hazard for an embedded frontend (the host may have its own COM apartment) in exchange for at most one component hard-labelled "Computer". `docs/cross-platform.md` is the audit this policy is maintained against — read it before touching anything platform-shaped. What the audit already produced, and must not be regressed: (a) `dedupe_disks` never collapses an EMPTY name — the name is a device identity on macOS/Linux but the volume LABEL on Windows, routinely blank, so two unlabelled volumes keyed on `""` merged into one row and the loser silently stopped being evaluated by the disk rule; (b) process-group roots no longer depend on the init/launchd anchor alone — `is_plausible_parent` rejects a ppid whose process started AFTER its alleged child, which is proof of pid reuse. Unix hides the problem by reparenting orphans to `INIT_PID`; Windows leaves the dead parent's pid in place and hands that number to someone else, and since `process_groups` feeds `AppCpu`/`AppMemory`, the damage was two live rules evaluating a fabricated aggregate rather than merely a wrong row. Deliberately conservative — only a start time known on BOTH sides and strictly later on the parent rejects the link, so same-second reuse still slips through and no existing behaviour changes; (c) `phys_footprint_bytes` is no longer macOS-only: Windows reads `PROCESS_MEMORY_COUNTERS_EX.PrivateUsage` (which sysinfo already fetches for every process and also surfaces as `virtual_memory`, so it costs nothing) and Linux reads `RssAnon + VmSwap` from `/proc/[pid]/status` (one small read per process; `smaps_rollup`'s `Pss + SwapPss` is more precise but walks every VMA, far too expensive over the full table each refresh). This matters because the byte ceilings (4 GiB / 8 GiB) were calibrated ON footprint — without an analogue the same number silently measured RSS and fired on roughly a third as much. `parse_proc_status_footprint` is `cfg(any(linux, test))` so the reference platform's `make check` still tests it; (d) `Capabilities` (`snapshot.rs`, on every `SystemSnapshot`, `serde(default)`) states what the BUILD can measure — `memory_footprint`/`memory_pressure`/`cpu_perf_levels` — so a `None` can be read as "not on this platform" rather than "not right now", and a frontend attached to a daemon reads the DAEMON's answer instead of guessing from its own build; per-value reasons (EPERM) would need an `Unavailable { reason }` and are not done. `ActiveThresholds::supports(AlertKind)` is the rule-level counterpart and `any_enabled()` now requires support, so a Windows/Linux build with only the pressure rule left on reports alerting as OFF instead of offering a settings control that can never fire.

## Conventions

- **All project documentation is in English** (this file, README, rustdoc, code comments), and so are CLI messages and logs. The only remaining Chinese content is the design doc (`collector-core-design.md`), which predates this rule.
- Every `.rs` file starts with the Apache 2.0 copyright header — do not omit it in new files.
- Error types are defined with snafu using struct variants (e.g. `SinkError::Remote { message }`). Beware selector-name clashes: same-named variants across enums in `error.rs` need `#[snafu(context(suffix(...)))]` (see the two `Timeout` variants). When adding variants that wrap an underlying failure, prefer a `source` field and snafu's context-selector idiom over stringifying.
- The CLI lives in `src/bin/zstats/` (`main.rs` hand-rolled arg parsing + `render.rs` text rendering + `daemon.rs` serve/attach/stop + `settings.rs`, a thin wrapper holding the `--config-dir` OnceLock over `zstats::settings`) and deliberately avoids clap; the lib contains no presentation logic. Watch-mode sections must keep a stable height: the NET table always shows the top `NET_ROWS` interfaces by current traffic (idle fill prefers en*/lo* names) instead of filtering to active ones — a per-tick row count makes everything below jump in the in-place repaint. The CLI surface is deliberately tiny: bare `zstats` = foreground live view with EVERY cadence forced to a fixed 2s beat (`foreground_config`; throttles are for the daemon); `zstats serve` = background mode driven entirely by the config file (detaches by default, `--foreground` to stay); `--json`/`--pretty` = one-shot snapshot. There are NO per-setting runtime flags — all tuning goes through `-add <key> <value>` / `-remove <key>` / `-list`, which edit `<config-dir>/config.toml` via the key table in `settings::apply_add` (kebab-case keys → typed fields, validated). Keep `USAGE` and `settings::KNOWN_KEYS` in sync when adding keys.
- The daemon (unix only) serves a per-user Unix socket (`$TMPDIR/zstats-$USER.sock`) with a line protocol: client sends `ATTACH`/`STOP`; `ATTACH` gets `HISTORY <n>` + n JSON snapshots (ring buffer, retention by timestamp span) then a live JSON stream. The client half of the protocol lives in the lib (`zstats::client`, `client` feature) — the bin's `daemon.rs` keeps the server plus the TUI wrapped around `DaemonStream` (attach warms the rolling averages from history before rendering) and re-exports `socket_path`/`is_running` from it; change the wire format only in `src/client.rs` + `daemon.rs` together, with the protocol tests in `tests/integration.rs::client_protocol`. The accept loop treats accept errors as per-connection and keeps serving (only a broken listener — NotConnected/BrokenPipe/AddrNotAvailable — stops it): breaking out on the first EMFILE/ECONNABORTED left a daemon that still collected but never answered again, and since the socket stays bound `is_running` kept reporting true while attach and stop hung forever. A connected peer that sends no command line within `COMMAND_TIMEOUT` (10s) is dropped rather than holding a task for the daemon's lifetime. SIGPIPE is reset to default in main so piped output dies silently.
- Daemon logging: serve (and only serve — a subscriber would corrupt the foreground TUI) installs tracing-subscriber writing timestamped lines to stderr, which the detached daemon appends to `$TMPDIR/zstats-$USER.log`. This also surfaces the lib Scheduler's tracing warnings, which are otherwise dropped. Level via `ZSTATS_LOG` (default info; `debug` shows per-round alert window state — the former `ZSTATS_ALERT_DEBUG` is gone). Alert/reload/lifecycle events log via `tracing::info!`/`warn!`/`debug!`, never `eprintln!`.
- Daemon alerting is split rules/delivery: the rule engine lives in the lib (`zstats::alerts`, `frontend` feature — Thresholds, 1-minute windows via `zstats::rolling`, per-(pid, rule) cooldowns, the recording criteria; every behavior test lives there too), while `src/bin/zstats/alerts.rs` keeps only this frontend's reactions — `AlertSink` wraps `AlertEngine` in a Mutex, hot-reloads thresholds, sends desktop notifications, and persists records. Notifications go via osascript on macOS / notify-send elsewhere; the helper's exit status IS awaited (tokio process, `NOTIFY_TIMEOUT` 2s so a wedged helper cannot eat the scheduler's 5s sink budget) and failures log a warning. A round's notifications are delivered CONCURRENTLY (one spawned task each, all awaited) rather than one after another: the engine has already marked every event as notified, so a sink that ran out of its 5s budget partway down the list dropped the rest permanently — episode state never re-offers them, and serially that needed only three alerts and a slow helper — fire-and-forget made "rule fired" and "user was told" indistinguishable in the log, which is the one thing you need when a notification goes missing. Delivery TIMING is still outside our reach: macOS may defer an accepted notification into a scheduled summary or hold it behind a Focus mode (`dndMirrored`/`dndDisplaySleep` auto-DND), so "osascript accepted the notification" (debug) is the strongest claim the daemon can make. Do NOT switch to notify-rust/notification-center APIs: identities masquerading as Terminal.app are silently dropped on this setup (show() still returns Ok, so no fallback is possible) — this was tested empirically; only the Script Editor identity (which osascript uses) displays. Rule semantics (two tiers per CPU rule, sharing one `alert-cpu` value and one per-(pid, kind) cooldown so the same situation never notifies twice): acute/runaway = 1-min average ≥ `ACUTE_FACTOR` (3) × the process's EFFECTIVE threshold — the factor multiplies the override, not the base, or template'd apps (a video call at 100%+) would be re-noised; chronic = average over `SLOW_FACTOR` (5) acute windows (`SLOW_WINDOW`/`SLOW_MIN_SPAN` derive as 5× `WINDOW`/`MIN_SPAN` = 300s/250s — the ratio is the design parameter, not the absolute) ≥ the effective threshold — one acute period cannot distinguish a self-limiting burst from "genuinely always busy", several can. Memory (`alert-mem`, default 25% of total, AND `alert-mem-bytes`, default 4 GiB — the effective bar is the LOWER of the two) is chronic-only by design: transient legitimate spikes must not alert. Two halves because neither works alone — a share of total RAM scales the wrong way (25% of 8 GiB is a browser tab on an ordinary morning; 25% of 64 GiB is never reached until long after the machine is swapping, and measured on a 24 GiB machine over 5 days the largest process ever recorded was 19.4%, i.e. the rule had never fired once), while a fixed byte count is too high for a small machine. So the percentage protects small machines, the ceiling protects large ones, and the rule means the same thing on both. `alert-mem 0` disables the whole rule (the ceiling and the template are refinements of it and cannot outlive it); `alert-mem-bytes 0` only removes the ceiling; a per-name override REPLACES both halves, since an override is an explicit request rather than a default (`ActiveThresholds::memory_bar_bytes` is the resolver, `memory_base_bytes` the override-free one recording uses). The ceiling is 4 GiB rather than the 2 GiB an 8 GiB machine implies because the measurement is `ProcessStats::footprint_avg_bytes` (the `phys_footprint` average, falling back to RSS where the kernel refused): a leak whose pages get compressed reads as a SHRINKING resident size — measured live, rust-analyzer held 3.02 GiB of footprint against 0.17 GiB of RSS — so a fixed byte bar catches roughly 3× as many processes under footprint as the same number would under RSS. `MetricRecord` carries `memory_footprint_bytes` alongside `memory_avg_bytes` for the same reason: a history that only had RSS could not explain its own alerts. The `[mem]` template table (tiers 30 = "judge it by share of the machine, no ceiling" for browsers/IDEs/language servers/DBs, 0 = never for VM hosts and your own toolchain) is what keeps this bar shippable — without it, rustc/rust-analyzer/qemu trip it on any developer machine within a day. Whole-application rules (`alert-app-cpu` 200 single-core %, `alert-app-mem` 40% of total AND `alert-app-mem-bytes` 8 GiB, both with `name=pct` overrides keyed on the group root name) run the same chronic machinery over `process_groups` — `ProcessWindows` keys on pid, and a group's ROOT pid plays that role — so the browser holding 4 GiB across 37 helpers is visible even though no member trips the per-process bar; chronic-only on purpose, since a runaway member is already the per-process acute tier's job and an acute group tier would just notify twice about one event. `alert-app-mem` has the SAME two halves and the same basis as the per-process rule, and for the same reasons found the same way: percentage-only, 40% is 9.6 GiB on a 24 GiB laptop and 25.6 GiB on a 64 GiB desktop, so the rule was unreachable on exactly the machines that run those browsers; and RSS-only, a group's resident sum FALLS as the kernel compresses it, i.e. shrinks precisely while the group is squeezing the machine. So `ProcessGroupSnapshot::phys_footprint_bytes` sums member footprints over the FULL table (with that member's RSS standing in wherever the kernel refused one, so the total is never silently partial and never worse than the resident sum it replaces; `None` only when no member had a footprint at all, i.e. off macOS), and `ActiveThresholds::app_memory_bar_bytes` resolves min(share, ceiling) with an override replacing both halves — `memory_bar_bytes` one level up. The ceiling is deliberately 2× `DEFAULT_MEMORY_BYTES` so the app bar stays above the per-process bar at every machine size (a test asserts this): a group alert then always means "more than any single process bar would have explained", and the two rules can never notify about one event. Cost of summing footprints over the full table rather than the top-N: one `phys_footprint` call per process (~0.5µs), a few hundred microseconds on the process cadence — and it has to be the full table, since summing after top-N truncation undercounts exactly the many-small-helper apps the rule exists for. Note the cooldown map is shared across rule kinds, so the per-process "forget dead pids" retain MUST exempt `AppCpu`/`AppMemory` entries (a group root need not appear in the top-N list; wiping them re-fires every group alert every round — this was a real bug caught by the tests). Defaults: CPU 30% single-core units. Disk capacity (`alert-disk`, default 90% used per volume) is crossing-based, not windowed: one alert on the upward crossing, silent while the volume stays full, re-armed after dropping `DISK_REARM_MARGIN` (5 points) below — no cooldown involved; per-mount `mount=pct` overrides (0 silences a volume — Time Machine targets run near-full by design). System memory pressure (`alert-pressure`, macOS): `off | warning | critical` (`settings::PressureAlert`, default warning; the key's original `true`/`false` still deserializes) selects which kernel `pressure_level` verdict interrupts. Requires PERSISTENCE, not just a crossing — measured on real data, a memory-heavy machine sits at warning as its steady state and flapped across the line ~4×/3h with values indistinguishable from normal, so plain crossing detection was pure noise; the episode must last `SLOW_WINDOW` (5m) for warning or `WINDOW` (1m) for critical, mirroring the acute/chronic "more severe = faster" split. The episode is SYMMETRIC: it ends only after the kernel reports normal continuously for `PRESSURE_REARM` (= `SLOW_WINDOW`, 5m), because a single normal sample used to re-arm the rule and the kernel level is a noisy step function — a machine near the line dips back for a sample or two regularly, so one continuous condition was chopped into a string of alerts that each arrived as news (measured in the daemon log: 4 warning alerts in 5.5h, every one of them `repeat=false`, i.e. never a repeat — the rule had no repeat path at all). It takes the same evidence to declare the episode over as to declare it started. This is also the ONE rule family whose reminders repeat indefinitely instead of stopping after one: pressure is a machine STATE rather than a culprit (there is nothing to kill, and it legitimately holds for a whole workday), so a still-unrecovered episode re-notifies on a BACKING-OFF schedule — the gap starts at `PERSIST_REMINDER` (30m) and doubles up to `PRESSURE_REMINDER_MAX` (4h), giving 30m/1h/2h/4h/4h… ≈ 6 notifications across 12h, each carrying `repeat_after` so it reads as "still going" and not as a new event. `repeat_after` counts from the episode's FIRST alert (same meaning as every other rule) while `sustained` counts from when the level first went above normal. One FIRST alert per severity: worsening escalates immediately (persistence is already established) and resets the backoff to 30m, since a new severity is genuinely new news; improving inside the episode is silent. Every pressure alert carries `AlertDetail::Pressure::top_consumers` (up to `PRESSURE_TOP_CONSUMERS` = 3 `MemoryConsumer`s above `PRESSURE_CONSUMER_FLOOR` = 5% of RAM, biggest first): whole applications from `process_groups` where they are collected — you quit Chrome, not `Google Chrome Helper (Renderer)` pid 41213 — individual processes otherwise. BOTH paths rank on the footprint (`phys_footprint_bytes.unwrap_or(memory_bytes)`): the kernel only reports pressure once it is compressing hard, so ranking groups by RSS demoted exactly the applications responsible for the episode being reported. This is the actionable half of the alert, and it is knob-free on purpose: unsmoothed because memory is a state rather than a rate, and with no user-facing bar because a bar you could raise would silence the list exactly when every consumer is medium-sized, which is when the names help most. `alert-cooldown` deliberately does NOT apply here — the 5m re-arm already floors new episodes at 10m apart, and a cooldown would swallow a genuine critical that follows a warning episode by 6 minutes. Auto-adaptive thresholds were considered and rejected: a rule that relaxes because you are always over it eventually alerts on nothing, and it destroys the "why did/didn't it alert" explainability that every other rule here has; the recorded history is instead the raw material for a future explicit *suggest* command. `compressed_bytes` deliberately has NO rule of its own (a big compressor with normal pressure is healthy macOS behavior — the kernel already folds compressor growth into the level; alerting on it would duplicate a better signal with a worse one). Note used% would be even worse (macOS runs high-used by design). Network and per-process/system disk-IO alerts were evaluated and deliberately rejected: per-process network attribution needs private APIs, so a network alert cannot name a culprit (not actionable), and sustained high IO is dominated by legitimate work (Spotlight, backups) while the real threat — a runaway writer — is caught by the capacity rule anyway. Both keys accept `name=pct` per-process overrides (case-insensitive, 0 disables that process), e.g. `-add alert-cpu ghostty=100`. Everything lives in the `[alerts]` section of the config file; serve reads it at startup (malformed file = fail fast, not silent defaults) and hot-reloads it by polling its mtime every 30 collects (`RELOAD_CHECK_EVERY`, ~1min at the default interval); a file that fails to parse on reload keeps the previous settings and logs to stderr. The old CLI-flags merge layer (`AlertCliOptions`) was dead code after the `-add` migration and was removed — thresholds merge is `ActiveThresholds::from_config` with per-name precedence: user override > builtin template > base value. An override KEY is an `alerts::Matcher`, not a plain name: a leading and/or trailing `*` makes it a Prefix/Suffix/Contains pattern, and a `*` anywhere else is REJECTED by `settings::apply_add` rather than stored as a literal (a key that looks like a pattern must never quietly match nothing). This exists because a process name is not a stable identifier — Zed ships rust-analyzer as `rust-analyzer-<date>` and rewrites that name on every update, so the old exact `rust-analyzer` template entry had never once matched on any Zed install and the indexer alerted against the 30% base (confirmed in a real daemon log: `threshold 30%`); the same pattern also covers sibling processes like `rust-analyzer-proc-macro-srv`, which auto-stripping a version suffix would not. Precedence is `(user layer, is_exact, literal length)`, highest wins, ties keeping the first entry — it has to be an explicit rank rather than "first match in file order" because the config's override maps are `BTreeMap`s, so what reaches `from_config` is alphabetical and not the order anything was written in. Matching is ASCII-case-insensitive and done on bytes (no allocation, no char-boundary slicing on arbitrary UTF-8 names). Template entries push via `with_template_override`; user entries via `with_override`. Consolidating the ~10 `X Helper (Renderer)` template entries into one `*Helper (Renderer)` is possible now but deliberately NOT done — it would extend the raised bar to un-vetted Electron apps, which is a behavior change and belongs in its own decision. The template is DATA IN A FILE, not a table in the source, and there is ONE FILE PER PLATFORM (`templates/alerts.toml` macOS + other unixes, `alerts-linux.toml`, `alerts-windows.toml`) selected by `cfg(target_os)` at the `include_str!`: process names are not portable at all — `Google Chrome Helper (Renderer)` is `chrome.exe` on Windows and `Isolated Web Co` on Linux, where the kernel truncates `comm` to 15 BYTES (so any Linux key longer than that matches nothing, which `every_platform_template_parses_from_any_platform` asserts along with parsing all three files on whatever platform runs the tests — only one is compiled into a given binary, so without that test a Windows typo ships and looks exactly like a quiet machine). Separate files rather than sections in one keep `deny_unknown_fields` strict, and `<config-dir>/template.toml` still replaces whichever was selected. The selected file is `include_str!`'d as `alerts::BUILTIN_TEMPLATE`, parsed once into `alerts::Template` (`version` + `[cpu]`/`[mem]`/`[app_cpu]`/`[app_mem]` BTreeMaps) behind a `OnceLock`. `Template::parse` rejects a version mismatch, an unknown table (`deny_unknown_fields`) and any key `Matcher::parse` refuses — a template is only useful if you can trust every line took effect. The move was only safe AFTER the `Matcher` work, because precedence used to depend on the const array's write order and a TOML table is a `BTreeMap` (alphabetical); it also deleted the ~120-line hand-synced reference copy in `config.example.toml`, which is why that "keep them in sync" instruction is gone. `settings::load_template(dir)` reads `<config-dir>/template.toml` if present and REPLACES the builtin wholesale (layering would make a removed entry unremovable and turn 3 precedence levels into 5; to ADD one entry you use a user override, which outranks either template anyway) — a missing file falls back to the builtin, but a malformed or wrong-version one is an ERROR at startup and keeps the previous thresholds on reload, never a silent fallback, since a template that quietly did not apply is indistinguishable from a quiet machine. `ActiveThresholds::from_config` = `from_config_with_template(file, Template::builtin())`. The daemon's mtime poll watches BOTH files (`source_mtimes()`) and applies a reload only when both halves load, so refreshing the table on a schedule is a `curl -o ~/.zstats/template.toml` cron line rather than an HTTP client inside a local metrics collector — a built-in fetcher was designed and deliberately deferred (it would be this exact machinery plus a downloader; the open question is only the dependency, `ureq` over `reqwest` if it ever lands, plus the trust note that whoever controls the URL can zero every threshold and silently end all alerting). The template file (~144 processes that legitimately sustain CPU: browsers/Electron 100, IDE indexers and VM hosts 200, work you started yourself and periodic macOS system work 0 — the 0 tier's dividing line is WHO ASKED, not how much CPU: compilers/linkers/build drivers (`rustc`/`cargo`/`clang`/`ld`/`make`/`ninja`/`go`, plus `git` auto-gc) are exempt because "your build is building" is not actionable, while a background indexer pegged for minutes IS a real failure and keeps a raised bar instead. Interpreted toolchains — `tsc`, gradle, webpack — are deliberately absent since they run under `node`/`java`, names that cover half the real runaways) applies unless `alert-template false`; the same switch also applies the file's `[app_cpu]`/`[app_mem]` tables to the whole-app rules. A template layer is skipped entirely when its BASE value is disabled (`alert-cpu 0` must mean "no CPU alerts", not "~60 templated apps keep firing"); an explicit user override is a request rather than a default and still applies over a disabled base. Those two are deliberately ~20 entries rather than 60, and their most important entry is not an app at all: on macOS every terminal session's descendants group under a `login` root (measured: 6 of 14 multi-process groups on a working machine), so a build sustains hundreds of percent under a non-application name — `login`/`tmux`/`sshd` and VM hosts are set to 0 (you started that work, and a genuine runaway among the members is still caught per-process), while browsers and IDEs get a raised bar (cpu 400 / mem 60) instead of an exemption; a same-name user entry always shadows it, and template entries never affect metrics recording (which uses base thresholds only). Note `socket_path()`/`log_path()` live under `$TMPDIR` — tests must override both `HOME` and `TMPDIR` (short path: unix sockets cap at ~104 bytes) or they will collide with the user's real daemon. Interactive alert dialogs (buttons on notifications) were tried and removed by user choice — banners cannot carry buttons for unbundled CLIs and the `display dialog` alternative was judged too intrusive; don't reintroduce without being asked. Every rule family is EPISODE-based (`EpisodeState`): a condition notifies once when it crosses, then exactly one follow-up if it is still true after `PERSIST_REMINDER` (30m, message suffixed "still going after N min" so it cannot read as a new event), then stays silent, and re-arms when the value falls back under the threshold or the process/group/volume disappears. Memory pressure is the documented exception on both halves — its reminders repeat forever on a doubling backoff and its re-arm needs 5m of sustained normal (see above); it also keeps its own state fields rather than using `EpisodeState`, which has no backoff concept. The follow-up exists because notify-once-forever has its own failure mode — a single notification can be missed, and on macOS it demonstrably can be deferred behind a Focus mode or notification summary — `alert-cooldown` (default 600s) is the minimum gap between episodes for one (pid, rule), a flapping floor rather than a repeat timer. This replaced per-cooldown re-alerting after a real machine produced 15 identical notifications for one pegged system daemon; it also makes the process/app rules consistent with the disk and pressure rules, which were episode-based from the start.
- Daemon metrics recording (criteria in `zstats::alerts`, file format in `zstats::records`, persistence wiring in the bin's `alerts.rs`): once per minute (`RECORD_EVERY`), every process whose 1-min average CPU or memory share exceeds the **base** alert thresholds is appended as one JSON line to `<config-dir>/data/YYYY-MM-DD.jsonl` (local date), PLUS the `RECORD_TOP_CPU_TIME` (5) processes that consumed the most CPU *time* in that window regardless of any threshold. That last criterion exists because every rule here compares an average against a bar, which structurally cannot see a process sitting at a steady 8% — yet 12h of that is ~1 core-hour, several times what a ten-minute runaway costs. It stays a RECORDING criterion and never an alert: a low-bar/long-window rule would fire on every legitimate resident daemon, and a 12-hour window rarely even completes on a laptop. The selection ranks by `ProcessStats::cpu_time_delta_ms` (the window's consumption) but the file stores `ProcessSnapshot::cpu_time_ms` — the process's LIFETIME counter, absolute — because a process is only recorded on the minutes it qualifies, so summing per-window deltas would silently undercount anything drifting in and out of the selection, whereas differencing a cumulative counter stays exact across gaps (a decrease means pid reuse). `cpu_time_ms` itself is free: sysinfo fills it from the same `task_info` call that produces `cpu_usage` under the refresh kind we already request. Process GROUPS deliberately carry no such counter — their membership churns, so a summed counter would drop whenever a helper exits and break the "diff two samples" contract. Per-process overrides deliberately do NOT apply here — an override silences the notification but the data point is still recorded (recording is history, alerting is interruption); disabling a base rule (0) disables that criterion for recording too. Retention is built into `records::append` (user decision): the first append of each local date per config dir sweeps files older than `records::RETENTION_DAYS` (30) — keyed off the caller-passed date (the module still never reads the clock), tracked in a process-wide per-dir map, logged via tracing. Every writer (daemon, GUI, example) gets cleanup for free with no bin-side scheduling; the accepted trade-off is that a quiet stretch with no appends leaves expired files until the next append. No config keys — cadence and retention are constants. `records::read_range` is the read API a GUI charts from.
